# ADR-002: Message Delivery Guarantees

## Status: Accepted

**Date:** 2026-04-05  
**Author:** Phenotype Engineering Team  
**Project:** bus

---

## Context

The event bus must decide on delivery guarantees: at-most-once, at-least-once, or exactly-once. This affects reliability, complexity, and performance.

### Requirements

1. **Best Effort**: Messages may be lost (acceptable for internal events)
2. **No Ordering**: Events don't need strict ordering
3. **Performance**: Low latency preferred over reliability

---

## Decision

We will use **at-most-once delivery with non-blocking send**:

```
┌────────────────────────────────────────────────────────────────┐
│              Delivery Guarantee: At-Most-Once                 │
│                                                                 │
│  Publisher                                                      │
│     │                                                           │
│     │ Publish()                                                 │
│     ▼                                                           │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  For each subscriber:                                     │   │
│  │                                                         │   │
│  │  select {                                                │   │
│  │      case ch <- msg:    // Success                      │   │
│  │      default:           // Channel full                 │   │
│  │          // DROP MESSAGE                                  │   │
│  │          log.Warn("subscriber channel full")             │   │
│  │  }                                                       │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────┐                                                    │
│  │ Result: │  Message delivered 0 or 1 times                   │
│  │         │  No retries, no persistence                       │
│  │         │  Fast, simple, may lose messages                    │
│  └─────────┘                                                    │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

### Rationale

| Guarantee | Pros | Cons | Verdict |
|-----------|------|------|---------|
| **At-most-once** | Fast, simple | May lose messages | **SELECTED** |
| At-least-once | Reliable | Requires buffering | Rejected |
| Exactly-once | Perfect | Complex, slow | Rejected |

### Implementation

```go
func (eb *EventBus) Publish(eventType string, payload interface{}, metadata map[string]string) error {
    msg := Message{
        ID:        generateID(),
        EventType: eventType,
        Payload:   payload,
        Metadata:  metadata,
        Timestamp: time.Now(),
    }
    
    eb.mu.RLock()
    subscribers := eb.subscribers[eventType]
    eb.mu.RUnlock()
    
    for _, ch := range subscribers {
        select {
        case ch <- msg:
            // Success
        default:
            // Channel full - drop message
            eb.logger.Warn("subscriber channel full", "type", eventType)
        }
    }
    
    return nil
}
```

---

## Consequences

### Positive

- **Fast**: Never blocks publisher
- **Simple**: No retry logic
- **Predictable**: No queue buildup

### Negative

- **Message loss**: Full channels drop messages
- **No guarantee**: Subscribers may miss events
